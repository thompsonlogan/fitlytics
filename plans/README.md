## Findings considered and rejected

(Recorded so nobody re-audits them.)

Round 1:

- **Pagination on program/video list endpoints**: all lists are per-user and
  structurally small (a user's own programs/videos); no unbounded growth path
  exists while the API is read-only.
- **GORM 6-level `Preload` in `GetProgramById`**: one query per level, not
  N+1; bounded by program size. Fine.
- **CSRF tokens**: SameSite=Lax cookies + all state changes on POST/PATCH +
  same-origin deployment (nginx proxies `/api` and `/auth`) already cover the
  attack surface.
- **Frontend bundle size / code splitting**: landing and today routes are
  already lazy (`lazyRouteComponent` in `router.tsx`).
- **`lib/pq` as a "duplicate" Postgres driver**: it's a real dependency of
  the GORM gen output (`pq.StringArray` in
  `internal/models/generated/exercises.gen.go`), not redundant.
- **Versioned migration lacking `IF NOT EXISTS` on some indexes**: V1 is a
  versioned (run-once) migration; the guard convention materially matters for
  repeatables, which comply.

Round 2:

- **`/healthz` DB-ping as a DoS vector**: not proxied by nginx (internal
  network only) and the ping uses a pooled connection; negligible.
- **Unpinned `flyway/flyway:latest` in the dev compose**: dev-only
  clean-migrate flow; the production runner is correctly pinned to
  `11-alpine`.
- **Mobile component render tests**: the behavior lives in
  `useDayBoard`/`useCellLogging`, which plan 001 covers; the mobile files are
  presentational pass-through.
- **`sessions_active_day_uq` limiting each program day to one session ever**:
  a documented V1 product decision (see the schema comments around the
  index), not a defect.
- **SidePanel comparing this week's planned vs last week's actual volume**:
  deliberate per its own comment ("Planned (this week) vs actual (last
  week)").
- **WorkOS SDK global state in `users.Service`/`WorkOSClient.GetUser`**: the
  handler-side seam is plan 014; the users-service path already has tests via
  its own fake and is deliberately left on the global config (noted in 014's
  maintenance notes).

## Direction notes (maintainer decisions, not plans)

Surfaced during the audits; each needs a product decision before planning:

1. **History page first.** `/program`, `/history`, `/analytics` are all
   nav-linked 404s. The schema already has a purpose-built index for history
   queries (`set_logs_user_exercise_completed_idx`,
   `database/flyway/sql_versioned/V1__001_init.sql:400`), making per-exercise
   history (last/best sets, load over time) the cheapest of the three to
   build. Analytics needs History's queries anyway.
2. **Program creation path.** The landing page markets a builder
   (`frontend/src/components/landing/builder-mock.tsx`) but the API is
   read-only — programs exist only via seed SQL. A minimal "create from
   template" endpoint would also fix the root cause behind plan 003.
3. **Unit preference & timezone are schema/API surface with no behavior.**
   `users.unit_preference` and `users.timezone` exist and `/api/me` returns
   them, but the UI hardcodes imperial and nothing updates a profile. Either
   build the settings slice (PATCH /api/me + a preference-aware
   `lib/units.ts`, which plan 013 sets up) or drop the columns until real.
4. **Ad-hoc sessions are half-supported.** The schema allows
   `sessions.program_day_id IS NULL` "for ad-hoc sessions" and the (removed
   by plan 011) rest-day buttons gestured at activity logging, but no API
   creates one. The data model is already paid for if this is on the roadmap.
5. **API-served upload limits.** Plan 015 hardens the env-var path; the full
   fix is serving video limits from the API so the four config copies
   (backend env, frontend env, Dockerfile ARGs, vite test env) collapse to
   one. Needs a backend DTO change + client regeneration.
