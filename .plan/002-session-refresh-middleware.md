## Why this matters

The backend issues 5-minute access-token cookies
(`backend/internal/handlers/auth.go:18`: `accessCookieTTL = 5 * time.Minute`).
Only ONE code path knows how to recover from expiry: `fetchMe` in
`frontend/src/hooks/use-auth.ts` (401 → `POST /auth/refresh` → retry). Every
other call — including every set-log PATCH a user fires mid-workout — fails
outright once the cookie expires, and the workout UI misclassifies the 401 as
a validation error, showing "Invalid value" on the cell
(`use-cell-logging.ts:46–48` treats all 4xx alike). A typical workout lasts
30–90 minutes, so **every real user hits this within one session**. It never
reproduces in development because `AUTH_BYPASS_USER_ID` skips token auth
entirely.

Fix: a refresh middleware on the generated OpenAPI client so a 401 on any
`/api/*` request triggers one single-flight refresh and one retry,
transparently. Also stop classifying 401/403 as cell-validation errors.

## Steps

### Step 1: Create the middleware

Create `frontend/src/services/auth-refresh-middleware.ts`:

```ts
import type { Middleware } from "./generated/runtime"

// Single-flight guard: many parallel 401s (React Query fires queries in
// bursts) must produce exactly one POST /auth/refresh. Module-level on
// purpose — all API classes share one middleware instance.
let refreshInFlight: Promise<boolean> | null = null

async function refreshSession(basePath: string): Promise<boolean> {
  const res = await fetch(`${basePath}/auth/refresh`, {
    method: "POST",
    credentials: "include",
  })
  return res.ok
}

// createAuthRefreshMiddleware returns a `post` middleware for the generated
// client: when an /api/* request comes back 401, refresh the session once
// (single-flight) and replay the original request. Non-/api/ paths (the
// /auth/* endpoints themselves) are ignored to make refresh loops
// structurally impossible. The replay uses the global fetch, NOT the
// middleware-wrapped one passed into the hook, so a still-401 replay cannot
// re-trigger this middleware.
export function createAuthRefreshMiddleware(basePath: string): Middleware {
  return {
    post: async ({ url, init, response }) => {
      if (response.status !== 401) return undefined
      if (!url.startsWith(`${basePath}/api/`)) return undefined

      refreshInFlight ??= refreshSession(basePath).finally(() => {
        refreshInFlight = null
      })
      const refreshed = await refreshInFlight
      if (!refreshed) return undefined // session is dead; let the 401 surface

      return fetch(url, init)
    },
  }
}

// Test-only reset so specs don't share single-flight state.
export function resetAuthRefreshState() {
  refreshInFlight = null
}
```

Notes for the executor:
- `Middleware` is exported by `frontend/src/services/generated/runtime.ts`
  (interface with optional `pre`/`post`/`onError`).
- The `post` hook receives a **clone** of the response, and returning
  `undefined` keeps the original — exactly what we want on the no-op paths.
- `basePath` is `""` in dev/prod (same-origin; see `main.tsx:15`), so the
  startsWith check degrades to `url.startsWith("/api/")` — correct for the
  relative URLs the client builds.

**Verify**: `pnpm typecheck` → exit 0.

### Step 3: Test the middleware

Create `frontend/src/services/auth-refresh-middleware.test.ts`. Stub the
global fetch with `vi.stubGlobal("fetch", fetchMock)`; call
`resetAuthRefreshState()` and `vi.unstubAllGlobals()` in `beforeEach`/
`afterEach`. Cases:

1. **Non-401 response** → `post` returns `undefined`; global fetch never
   called.
2. **401 on a non-/api/ URL** (e.g. `/auth/refresh` itself) → returns
   `undefined`; no refresh attempted. This is the loop-prevention property.
3. **401 → refresh 204 → replay 200**: `post` returns the replayed Response;
   fetch was called twice (refresh, then replay with the original `url` and
   `init`).
4. **401 → refresh 401** → returns `undefined` (caller sees the original
   401); fetch called once (refresh only, no replay).
5. **Single-flight**: fire the `post` hook twice concurrently (two different
   URLs, both 401) with a refresh mock gated on a manually-resolved promise →
   exactly one refresh call, two replays.
6. **Replay still 401** → the replayed 401 is returned as-is (no second
   refresh — the replay goes through raw fetch, and assert refresh was called
   exactly once).

Build fake `Response` objects with `new Response(null, { status: 401 })` /
`{ status: 204 }` — jsdom provides Response (the existing
`use-cell-logging.test.tsx` from plan 001 already relies on it).

**Verify**: `pnpm vitest run auth-refresh-middleware` → 6 tests pass.

### Step 4: Stop classifying auth failures as validation errors

In `frontend/src/components/workout/use-cell-logging.ts`, narrow `is4xx` so
401/403 fall through to the generic connection toast instead of an inline
"Invalid value" cell error (after this plan, a surfaced 401 means the refresh
already failed — the session is dead, and "Invalid value" would be a lie):

```ts
function is4xx(err: unknown): err is ResponseError {
  return (
    err instanceof ResponseError &&
    err.response.status >= 400 &&
    err.response.status < 500 &&
    err.response.status !== 401 &&
    err.response.status !== 403
  )
}
```

Update the plan-001 characterization test marked with the
`plan 002` note in `use-cell-logging.test.tsx`: a 401 rejection now asserts
`toast.error` was called and `cellErrors` stays empty.

**Verify**: `pnpm vitest run use-cell-logging` → all pass, including the
updated 401 test.
